Warm Imps: Lifecycle and Operations

Warm imps are the default path for non-interactive text runs. The first prompt starts a background --serve process; later prompts reuse it. The process is warm, but every prompt still gets a fresh ephemeral Codex thread.

Core Rule

Warm mode buys latency. It is not conversational memory, and requests are serialized through one resident app-server per imp.

Lifecycle

  1. 1

    Start

    Explicit non-interactive text calls such as --run, --exec, --non-interactive, and -q use warm mode unless --no-warm is passed. Input-image turns skip warm mode.

  2. 2

    Spawn

    If no reusable warm imp is listening, the client starts a detached copy of the same executable with --serve. Running imp-gh --serve directly keeps that server in the foreground for a supervisor.

  3. 3

    Ready

    The warm server starts codex app-server, completes the initialize handshake, then accepts a Unix socket connection. Client readiness polling defaults to CODEX_IMP_READY_TIMEOUT_MS=120000.

  4. 4

    Run

    Each request sends prompt, cwd, effort, quiet flag, and turn timeout over the socket. The warm server serializes requests and starts a fresh thread/start plus turn/start on the already-warm app-server.

  5. 5

    Hot Reload

    Before reuse, the client compares the current source fingerprint with warm metadata. If the imp executable or loaded runtime files changed, the old warm process is stopped and a fresh one starts before the prompt runs.

  6. 6

    Idle Shutdown

    Warm imps shut down after CODEX_IMP_IDLE_MINUTES, default 30, once no turns are active. Set it to 0 to disable idle shutdown.

  7. 7

    Manual Stop

    Use imps stop imp-gh for one warm imp or imps stop --all for the fleet. Use imps doctor when stale socket state is suspected.

Decision Table

Situation Do This Why
Repeated text prompts Let warm mode run Best default latency path.
One-off clean debug run Add --no-warm Avoids the resident process entirely.
Input images Expect the cold path Warm mode is skipped for image turns.
Need a supervised server Run imp-gh --serve Foreground process for launchd, systemd, or manual observation.
Prompt exceeds turn budget Use --timeout-ms, --turn-timeout-ms, or CODEX_IMP_TURN_TIMEOUT_MS Controls per-prompt work time.
Startup/readiness is slow Tune CODEX_IMP_READY_TIMEOUT_MS or CODEX_IMP_START_TIMEOUT_MS These are startup waits, not prompt waits.
Many old warm imps Run imps ps, then imps stop --all Cleans resident background processes.
Suspect stale socket state Run imps doctor Uses the supported cleanup path.
Edited imp/runtime source Run again, or force imps stop <name> if in doubt Fingerprint mismatch should restart stale warm state.

What Ready Means

Ready means the imp server has started codex app-server, completed initialization, and is accepting socket connections. It does not mean a user prompt has already started.

What Warm Does Not Mean

No prompt memory. Each call starts a fresh ephemeral thread. The reused part is process setup, auth/config load, app-server startup, and transport warmth.

Timeout Knobs

CODEX_IMP_IDLE_MINUTES=30

How long an inactive warm imp stays alive. Set 0 to disable idle shutdown.

CODEX_IMP_READY_TIMEOUT_MS=120000

How long the client waits for a newly spawned warm imp to accept socket connections.

CODEX_IMP_START_TIMEOUT_MS=180000

How long app-server RPC/startup waits can take before failing.

CODEX_IMP_TURN_TIMEOUT_MS=300000

Default per-prompt warm turn watchdog. Override one call with --timeout-ms or --turn-timeout-ms.

Under The Hood

The implementation uses a Unix socket at /tmp/codex-imp-{name}.sock and metadata at /tmp/codex-imp-{name}.meta.json. Treat those as implementation details. Prefer imps ps, imps stop, and imps doctor for normal operations.

If warm startup fails or the connection drops, the caller can fall back to a cold in-process SDK run. That fallback explains occasional slower calls without implying the imp is broken.
